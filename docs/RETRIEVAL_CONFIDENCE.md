# 检索证据充分性

## 排序与证据接受

候选排序回答“哪些片段相对更接近 query”，证据接受回答“这些片段是否足以支撑事实回答”。普通知识库搜索接口继续返回经过距离过滤和确定性重排的近似结果；进入 Chat、Agent、Interview、Evaluation、Job Analysis 和 Resume Prompt 的片段还必须通过数据库所有权、类别和充分性判断。

`RetrievalDecision` 在内部记录排序候选、接受候选、是否充分、置信度、原因枚举和过滤计数，不改变现有前端 API。日志只记录计数和原因枚举，不记录完整 query 或 chunk。

## 确定性接受策略

当前策略保持平方 L2 距离方向、70% 语义/30% 词项排序权重和 0.12 相邻近重复惩罚不变。接受判断使用以下信号：

- top 候选距离和高置信、边界、硬拒绝三个区域；
- 正文词项覆盖和完整技术词；
- 数据库可信文件名的辅助覆盖，文件名不能单独使候选通过；
- query 中明确数字是否在证据中出现；
- “多少”等数量问题是否有数值支持；
- 明确否定证据与“文档没有说明”的区别；
- 非重复内容是否提供额外支持；
- 技术词堆砌和 JD/other 类别过滤。

高置信区仍需通过数字、技术词和堆砌防护。边界区只有在词项、完整技术词、明确否定、可信文件名加正文或非重复支持足够时才接受。平方 L2 超过 `1.15` 的候选是硬拒绝区，不能因词项得分进入 Agent 证据。`EVIDENCE_MAX_DISTANCE=0.8` 保留为高置信参考，不再是唯一接受条件。

存在性 query 使用少量结构信号（如“是否”“有没有”“包含”），不会按固定问题文本或 case ID 分支。明确“未使用 Redis”可以作为否定回答的证据；“资料没有说明 Redis”不会被当成项目明确未使用 Redis。query 指定的数字必须在候选中一致出现，数量问题没有数值时返回 insufficient。

## 安全过滤顺序

1. Chroma 使用 `user_id` 过滤召回候选；
2. 校验 metadata 基本格式；
3. 一次批量查询 `FileRecord`，以数据库记录复核所有权、类别和文件名；
4. 排除 JD/other 和非法 chunk；
5. 确定性重排、去重和多样性处理；
6. 进行充分性判断；
7. 只有接受候选可以构造 source_id 和进入 Agent Prompt。

管理员执行普通 Agent 任务时不绕过该顺序。每次检索仍只有一次 `FileRecord` 批量查询，不存在按 chunk 查询的 N+1。

## 受控候选扩展

初次候选池仍为 `top_k * 3`。若初次结果填满候选池，且合法候选不足或边界仍开放，最多再查询 Chroma 一次；扩展后的候选上限为 40，不循环、不绕过所有权或硬拒绝区。空知识库和短结果不会扩展，`top_k` 仍表示最终最多接受数量。

development 中受控扩展触发 16/35，候选数 P50/P95 为 15/30，并将部分相关来源截断从 5 个 case 降到 3 个；validation 中触发 8/25，P50/P95 为 15/29，原本没有截断。扩展没有改善这两个集合的最终 Recall，因此它只解决“候选能否参与判断”，不被描述为排序质量提升。

## Validation 与 Holdout 纪律

- development：35 query / 48 chunk，只用于问题发现和有限调优；
- validation：25 query / 42 chunk，可用于方案选择；SHA-256 为 `4fbb3ff6c198d8cde99466d081744fdd4db7d972f1756ae3f1d4b8dae8917460`；
- final holdout：25 query / 42 chunk，只在生产文件哈希冻结后正式运行；SHA-256 为 `4b6444db54df4036310ece8900ffea1a41977f86f4510cef9cfdf9891d19ae72`。

两个新集合各包含 3 个虚构用户和 7 个无答案 query，case ID 和 chunk 原文与 development 及彼此均无精确重复。`retrieval_validation_manifest.json` 固定数据哈希；`retrieval_production_freeze.json` 固定生产文件哈希。最终 holdout 运行后没有修改生产逻辑、参数、fixture 或期望。

## 已知局限

- 三个集合均为小规模合成语料，不能代表生产查询分布；
- 词项规则不等价于完整中文语义分析，边界同义表达仍可能被拒绝；
- BGE 的相关/无关距离存在明显重叠，确定性规则无法完全消除；
- 自适应扩展减少了候选截断，但没有证明能稳定提升最终 Recall；
- 下一阶段需要全新的独立集合验证多跳、多证据和属性缺失问题，不能复用 final holdout 调参。
