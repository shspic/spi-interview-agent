## 1. 项目概述

### 1.1 项目名称

```
基于 RAG 的 AI 实习面试训练与岗位匹配助手
```

英文名可暂定为：

```
AI Interview RAG Coach
```

### 1.2 项目定位

本项目是一个面向 AI 实习求职准备的个人化面试训练系统。

系统支持导入用户的个人简历、项目经历、技术笔记、面试题库、STAR 故事等本地资料，并结合岗位 JD 进行岗位分析、自由问答和模拟面试。

系统回答问题时优先检索本地知识库；本地知识库不足时，允许调用 Tavily 联网搜索补充通用知识；如果仍然无法可靠回答，必须明确说明不知道，不能编造个人经历或项目经验。

### 1.3 第一版目标用户

第一版优先服务用户本人，用于准备 AI 应用开发、RAG、Agent、LangChain、Python 等方向的实习面试。

暂不面向多用户开放。

### 1.4 项目核心价值

本项目解决以下问题：

1. 用户的个人资料、学习笔记、项目经历分散，难以快速转化成面试回答。
2. 用户需要针对不同岗位 JD 分析匹配点、短板和面试问题。
3. 用户需要模拟面试训练，并获得结构化评分和改进建议。
4. 普通大模型容易编造个人经历，本系统通过本地知识库和来源约束降低胡编风险。
5. 项目可作为 AI 应用开发方向的简历项目，体现 RAG、FastAPI、React、LangChain、ChromaDB、联网搜索和本地历史记录等能力。

## 3. 用户场景

### 3.1 场景一：构建个人面试知识库

用户上传以下资料：

```
resume.mdself_intro.mdcareer_transition_reason.mdai_learning_plan.mdproject_experience.mdpython_notes.mdrag_notes.mdlangchain_notes.mdagent_notes.mdinterview_questions.mdstar_stories.md
```

系统读取文件，完成文本解析、切分、向量化，并存入 ChromaDB。

### 3.2 场景二：岗位分析

用户粘贴一个 AI 实习岗位 JD。

系统分析：

1. 岗位摘要。
2. 核心技能要求。
3. 用户已有匹配点。
4. 用户短板。
5. 简历优化建议。
6. 可能面试问题。
7. 优先准备清单。

### 3.3 场景三：自由问答

用户输入问题：

```
你为什么从工程造价转 AI 应用开发？
```

系统优先从个人知识库检索相关内容，生成可用于面试的回答，并显示依据、来源、追问和风险提示。

### 3.4 场景四：模拟面试

用户输入：

```
请开始模拟面试
```

系统要求用户选择面试类型：

```
综合面 / 项目面 / 技术面 / HR 面
```

系统结合岗位 JD 和个人知识库生成问题。用户逐题回答后，系统进行五维评分，输出点评、参考回答和下一题。

### 3.5 场景五：历史复盘

用户查看历史记录，包括：

1. 岗位分析记录。
2. 自由问答记录。
3. 模拟面试题目。
4. 用户回答。
5. 五维评分。
6. 改进建议。
7. 是否使用 Tavily。
8. 引用来源。

## 5.4 模拟面试模式

### 5.4.1 功能说明

用户开始模拟面试后，系统根据岗位 JD 和个人知识库动态生成问题。用户逐题回答，系统评分、点评，并继续下一题。

### 5.4.2 面试类型

用户可选择：

```
综合面项目面技术面HR 面
```

### 5.4.3 基本流程

```
用户点击“开始模拟面试”↓系统要求选择面试类型↓用户输入或粘贴岗位 JD↓系统根据 JD + 个人知识库生成第 1 题↓用户回答↓系统评分和点评↓系统给出参考回答↓系统生成下一题
```

### 5.4.4 每轮输出

每题回答后，系统输出：

1. 当前题目。
2. 用户回答摘要。
3. 五维评分。
4. 总分。
5. 主要问题。
6. 改进建议。
7. 参考回答。
8. 下一题。

### 5.4.5 模拟面试题量

第一版标准验收要求：

```
至少能完成 5 题模拟面试。
```

## 6. 评分规则

### 6.1 五维评分制

每题总分 100 分，分为 5 个维度，每项 20 分。

|评分维度|分值|说明|
|---|---|---|
|内容相关性|20|是否正面回答问题|
|个人匹配度|20|是否结合自己的经历、项目、学习背景|
|技术准确性|20|技术概念是否正确|
|表达结构|20|回答是否有逻辑、有层次|
|风险控制|20|是否存在夸大、编造、无法证明的内容|

### 6.2 评分输出格式

```
# 本题评分## 总分76 / 100## 评分明细- 内容相关性：18 / 20- 个人匹配度：14 / 20- 技术准确性：16 / 20- 表达结构：15 / 20- 风险控制：13 / 20## 主要问题你的回答提到了 RAG，但没有说明自己的项目里如何实现文档切分、向量检索和回答生成。## 改进建议补充一个具体项目例子，用“项目背景 → 技术实现 → 遇到的问题 → 改进方式”的结构回答。## 参考回答……
```

## 7. 知识来源策略

### 7.1 基本原则

系统必须遵守：

```
本地知识库优先；本地知识库不足时允许联网搜索；联网搜索只能补充通用知识；不知道就说不知道；不能编造个人经历。
```

### 7.2 本地知识库优先

涉及以下内容时，只能基于本地知识库回答：

1. 用户做过什么项目。
2. 用户掌握什么技能。
3. 用户有什么学习经历。
4. 用户有什么实习经历。
5. 用户为什么转 AI。
6. 用户的学校、专业、简历内容。
7. 用户的 STAR 故事。

如果本地知识库没有依据，必须提示：

```
当前个人知识库中没有足够依据确认该内容，不能替你编造。
```

### 7.3 Tavily 搜索使用范围

Tavily 只能用于补充：

1. 通用技术概念。
2. 岗位要求解释。
3. 行业背景。
4. 通用面试知识。
5. 技术关键词解释。
6. 常见 RAG / Agent / LangChain 面试题。

### 7.4 Tavily 禁止用途

Tavily 不能用于：

1. 编造用户项目经历。
2. 编造用户实习经历。
3. 编造用户能力水平。
4. 编造用户获奖情况。
5. 编造用户 GitHub 项目成果。
6. 把网上案例包装成用户经历。

## 8. 知识库充分性判断

### 8.1 判断方案

第一版采用：

```
相似度阈值 + LLM 二次判断
```

### 8.2 判断流程

```
用户输入问题↓ChromaDB 检索 top_k 个本地知识片段↓根据相似度分数初步过滤↓将问题和检索片段交给 LLM 判断↓LLM 输出 sufficient / partial / insufficient↓根据判断决定是否调用 Tavily
```

### 8.3 判断结果

|判断结果|含义|后续动作|
|---|---|---|
|sufficient|本地知识库足够回答|只基于本地知识库回答|
|partial|本地知识库只能部分回答|Tavily 补充通用知识|
|insufficient|本地知识库不足|Tavily 搜索；仍不足则说不知道|

### 8.4 判断约束

LLM 二次判断时必须输出结构化结果：

```
{  "status": "sufficient | partial | insufficient",  "reason": "判断原因",  "need_web_search": true,  "personal_info_risk": true}
```

## 10. 系统架构

### 10.1 总体架构

```
React/Vite 前端    ↓ HTTP APIFastAPI 后端    ↓文件解析模块    ↓文本切分模块    ↓Embedding 模块    ↓ChromaDB 向量库    ↓Retriever 检索模块    ↓充分性判断模块    ↓DeepSeek Chat / Tavily Search    ↓答案生成模块    ↓SQLite 历史记录
```

### 10.2 自由问答流程

```
用户输入问题↓前端 POST /api/chat/ask↓后端检索 ChromaDB↓相似度阈值判断↓LLM 判断知识库是否足够↓如果足够：基于本地知识库回答↓如果部分足够：Tavily 补充通用知识↓如果不足：Tavily 搜索或说明不知道↓生成结构化回答↓保存历史记录↓返回前端展示
```

### 10.3 岗位分析流程

```
用户粘贴 JD↓前端 POST /api/jobs/analyze↓后端提取 JD 技能要求↓检索用户本地知识库↓分析匹配点和短板↓生成岗位分析结果↓保存历史记录↓返回前端展示
```

### 10.4 模拟面试流程

```
用户选择面试类型并粘贴 JD↓POST /api/interview/start↓系统生成第 1 题↓用户提交回答↓POST /api/interview/answer↓系统评分↓系统生成参考回答和下一题↓保存本轮记录↓循环直到完成面试
```

## 19. 项目风险与控制

### 19.1 风险一：项目范围过大

控制方式：

```
第一版只做标准 MVP，不做用户系统、部署、语音、JD 管理。
```

### 19.2 风险二：RAG 检索不准

控制方式：

1. 调整 chunk_size。
2. 调整 top_k。
3. 使用 bge-small-zh-v1.5。
4. 显示引用来源。
5. 增加 LLM 二次判断。

### 19.3 风险三：模型编造个人经历

控制方式：

1. 个人经历只能来自本地知识库。
2. Tavily 只能补充通用知识。
3. 输出风险提示。
4. 回答中显示来源。
5. 无依据时明确说明不知道。

### 19.4 风险四：前后端联调复杂

控制方式：

1. 先完成后端接口。
2. 使用 Swagger 测试接口。
3. 前端只做简洁可用页面。
4. 每个模块单独联调。

### 19.5 风险五：本地 Embedding 安装困难

控制方式：

1. 优先使用小模型 bge-small-zh-v1.5。
2. 在 README 中说明首次运行需下载模型。
3. 提供备用方案：后续可切换 API Embedding。
